# How to submit package to CRAN

**Type:** How-To
**Audience:** Package Maintainers
**Last Updated:** 2025-10-26

## Overview

This guide provides step-by-step instructions for preparing and submitting the PowerAnalysisTool package to CRAN (Comprehensive R Archive Network). It covers all requirements, checks, and the actual submission process.

**Estimated Time:** 4-8 hours of work spread over several days (includes waiting for remote checks)

## Prerequisites

- Package development complete and tested
- All features working locally
- Git repository up to date
- R (>= 4.2.0) installed
- RStudio recommended (optional but helpful)

## Goal

Successfully submit the package to CRAN and pass the automated and human review process with zero errors, warnings, and notes.

---

## Understanding CRAN Requirements

### The Golden Rule

Your package **must pass R CMD check** with:
- **0 errors**
- **0 warnings**
- **0 notes** (or only unavoidable notes that are documented)

### Key CRAN Policies

1. **Valid maintainer email** - Must be real, monitored, and stable
2. **Complete documentation** - All exported functions need examples
3. **Multi-platform testing** - Must work on Windows, macOS, and Linux
4. **No bad behavior** - Cannot write to user directories, modify global options, or access internet without permission
5. **Open source license** - Must use standard license (we use MIT)
6. **Proper DESCRIPTION** - All metadata fields correctly formatted

## Step-by-Step Submission Process

### Phase 1: Add Examples to Exported Functions

**Time Required:** 2-4 hours

**Reference:** See `docs/002-how-to-guides/013-add-examples-to-exported-functions.md` for detailed instructions.

#### 1.1: Install Required Packages

```r
install.packages(c("devtools", "roxygen2", "rcmdcheck", "rhub"))
```

#### 1.2: Identify Functions Needing Examples

All 16 exported functions currently lack examples:

**Propensity Score Functions** (R/fct_propensity_score.R):
1. `calculate_bhattacharyya_coefficient()`
2. `calculate_n_li_2025()`
3. `calculate_power_li_2025()`
4. `compare_ps_methods()`
5. `estimate_ps_distribution_params()`
6. `generate_ps_sensitivity_analysis()`
7. `interpret_overlap_coefficient()`
8. `interpret_rho_squared()`

**Survival Non-Inferiority Functions** (R/fct_survival_ni.R):
9. `events_survival_ni()`
10. `interpret_hr_margin()`
11. `mde_survival_ni()`
12. `power_survival_ni()`
13. `ssize_survival_equiv()`
14. `ssize_survival_ni()`

**UI/App Functions**:
15. `create_app_header()` (R/app_ui.R)
16. `run_app()` (R/run_app.R or similar)

#### 1.3: Add Examples Using Template

For each function, add `@examples` section to roxygen block:

**Template for statistical functions:**
```r
#' @examples
#' # Calculate sample size for 80% power
#' result <- ssize_survival_ni(
#'   hr = 0.75,
#'   alpha = 0.05,
#'   power = 0.80,
#'   p = 0.5
#' )
#' print(result$n_per_group)
#'
#' # Higher power requires larger sample
#' result_90 <- ssize_survival_ni(hr = 0.75, power = 0.90)
#' print(result_90$n_per_group)
```

**Template for UI functions:**
```r
#' @examples
#' \dontrun{
#' # This function is designed for use within a Shiny app
#' ui <- fluidPage(
#'   create_app_header()
#' )
#' }
```

**Template for run_app():**
```r
#' @examples
#' \dontrun{
#' # Launch the interactive application
#' run_app()
#' }
```

#### 1.4: Regenerate Documentation

After adding examples to all functions:

```r
# Update man/ files and NAMESPACE
devtools::document()
```

**Expected output:**
```
ℹ Updating PowerAnalysisTool documentation
ℹ Loading PowerAnalysisTool
Writing NAMESPACE
Writing calculate_bhattacharyya_coefficient.Rd
Writing ssize_survival_ni.Rd
...
Documentation completed
```

#### 1.5: Test Examples Locally

Test that examples run without errors:

```r
# Test all examples
devtools::run_examples()

# Or test individual function
devtools::run_examples("ssize_survival_ni")
```

**Troubleshooting:**
- If examples fail, fix the code in the R source file
- Run `devtools::document()` again
- Repeat until all examples pass

### Phase 2: Local Testing

**Time Required:** 1-2 hours

#### 2.1: Run Local R CMD Check

This is the **most important** check:

```r
# Run check with CRAN settings
check_results <- devtools::check(cran = TRUE)
```

**What this does:**
- Builds the package
- Checks documentation completeness
- Runs all examples
- Runs all tests
- Checks DESCRIPTION and NAMESPACE
- Verifies vignettes build
- Checks for common issues

**Expected output (success):**
```
── R CMD check results ──────────────── PowerAnalysisTool 5.0.0 ────
Duration: 3m 42s

0 errors ✔ | 0 warnings ✔ | 0 notes ✔

R CMD check succeeded
```

**If you see errors or warnings:**
1. Read the error message carefully
2. Fix the issue in source files
3. Run `devtools::document()` if needed
4. Run `devtools::check(cran = TRUE)` again
5. Repeat until clean

#### 2.2: Review Check Results

Pay special attention to:

- **Examples section** - All examples must run successfully
- **Tests section** - All testthat tests must pass
- **Vignettes section** - All vignettes must build
- **Package dependencies** - All imported packages must be in DESCRIPTION

#### 2.3: Fix Common Issues

**Issue: "Undocumented code objects"**
- Solution: Add roxygen documentation and run `devtools::document()`

**Issue: "Examples failed"**
- Solution: Check and fix example code, ensure it's runnable

**Issue: "Package has CRAN incoming feasibility NOTE"**
- Solution: This is normal for new submissions, document in cran-comments.md

**Issue: "Non-standard file/directory found"**
- Solution: Add files to .Rbuildignore

### Phase 3: Multi-Platform Testing

**Time Required:** 2-3 hours (including waiting for remote services)

CRAN requires testing on multiple platforms. You have three options:

#### 3.1: GitHub Actions (Automated - Recommended)

**Already configured:** `.github/workflows/R-CMD-check.yml`

Push your code to GitHub:

```bash
git add .
git commit -m "docs: add examples to all exported functions for CRAN submission"
git push origin feature/golem-migration
```

Then visit: `https://github.com/YOUR_USERNAME/YOUR_REPO/actions`

**Expected:** Green checkmarks for all 4 test environments:
- ubuntu-latest (R-release)
- ubuntu-latest (R-devel)
- windows-latest (R-release)
- macOS-latest (R-release)

**Advantages:**
- Automated on every push
- Tests all required platforms
- Free for public repositories
- Easy to share results with CRAN

#### 3.2: Win-Builder (Windows Testing)

Test on Windows using CRAN's own infrastructure:

```r
# Test on R-devel (development version)
devtools::check_win_devel()

# Test on R-release (current stable)
devtools::check_win_release()
```

**What happens:**
1. Package is uploaded to win-builder
2. R CMD check runs on Windows
3. You receive an email with results (to maintainer email)

**Timeline:** Results typically arrive in 10-30 minutes

**Expected email subject:** `CRAN Submission Check: PowerAnalysisTool_5.0.0`

**Look for:**
```
Status: OK
```

#### 3.3: R-hub (Multi-Platform Testing)

R-hub provides testing on various platforms:

```r
# Check on multiple platforms
rhub::rhub_check()
```

**This will:**
1. Create GitHub Actions workflow in your repository
2. Test on various Linux, Windows, and macOS configurations
3. Provide results via GitHub

**Recommended platforms:**
- Windows Server 2022 (R-devel)
- Ubuntu Linux 20.04 (R-release)
- Fedora Linux (R-devel)
- macOS 10.13.6 High Sierra (R-release)

**Alternative (legacy rhub v1 if available):**
```r
rhub::check_for_cran()
```

### Phase 7: After Submission - What to Expect

#### 7.1: Automated Checks (Minutes to Hours)

After confirming, CRAN's automated system will:
1. Run R CMD check on multiple platforms
2. Scan for common issues
3. Check for viruses/malware
4. Verify policy compliance

**Timeline:** Usually 15-60 minutes

#### 7.2: Human Review (Hours to Days)

A CRAN volunteer reviewer will:
1. Review automated check results
2. Read cran-comments.md
3. Check code for policy violations
4. Test examples and vignettes
5. Make a decision: Accept, Request Changes, or Reject

**Timeline:** Typically 1-10 business days (often 2-3 days)

**During this time:**
- Do NOT submit updates
- Do NOT send follow-up emails (unless >2 weeks)
- Be patient - reviewers are volunteers

#### 7.3: Possible Outcomes

**Outcome 1: Accepted ✓**

**Email:** `CRAN Package PowerAnalysisTool approved`

**What happens:**
- Package is published to CRAN within 1-2 hours
- Appears at: https://cran.r-project.org/package=PowerAnalysisTool
- Available via `install.packages("PowerAnalysisTool")`

**Your response:** None required (optional thank you email)

**Outcome 2: Changes Requested**

**Email:** Lists required changes

**Example issues:**
- Missing documentation
- Examples that fail
- Policy violations
- Unclear DESCRIPTION

**Your response:**
1. Fix all requested issues
2. Increment patch version (5.0.0 → 5.0.1)
3. Update NEWS.md with changes
4. Re-run all checks
5. Resubmit with explanation of fixes

**Timeline for resubmission:** Usually allowed immediately

**Outcome 3: Rejected**

**Email:** Explains reasons for rejection

**Common reasons:**
- Serious policy violations
- Package doesn't work
- Not suitable for CRAN

**Your response:**
1. Address all issues completely
2. Consider if package is appropriate for CRAN
3. May need to wait before resubmitting

## Common Rejection Reasons and Prevention

### Top 10 Rejection Reasons

1. **Examples fail to run**
   - Prevention: Test with `devtools::run_examples()`

2. **Missing documentation**
   - Prevention: All exported functions must have examples

3. **Package doesn't build on all platforms**
   - Prevention: Test with win-builder and R-hub

4. **Violates CRAN policies**
   - Prevention: Read https://cran.r-project.org/web/packages/policies.html

5. **Writes to user's home directory**
   - Prevention: Use `tempdir()` for all file operations

6. **Invalid email address**
   - Prevention: Use real, monitored email (already done)

7. **Undocumented dependencies**
   - Prevention: All imported packages in DESCRIPTION

8. **Title not in title case**
   - Prevention: Check DESCRIPTION (already correct)

9. **Description too short**
   - Prevention: Must be >2 sentences (already done)

10. **Vignettes don't build**
    - Prevention: Test with `devtools::build_vignettes()`

## Troubleshooting Guide

### Issue: R CMD check takes very long

**Solution:**
```r
# Skip vignette building during development checks
devtools::check(vignettes = FALSE)

# Only build vignettes for final pre-submission check
devtools::check(cran = TRUE)
```

### Issue: Examples fail on CRAN but work locally

**Possible causes:**
1. Hard-coded file paths
2. System-specific code
3. Missing package dependencies
4. Timezone or locale issues

**Solution:**
- Use `tempdir()` for file operations
- Check `Sys.info()` in examples
- Ensure all packages in Imports/Suggests
- Use `\donttest{}` for system-specific examples

### Issue: Win-builder shows errors, but local check passes

**Common cause:** Windows-specific path issues

**Solution:**
- Use `file.path()` instead of `/` or `\`
- Test with `normalizePath()`
- Avoid hard-coded paths

### Issue: Package size too large

**CRAN limit:** 5 MB (soft limit, can request exception)

**Check size:**
```r
# Build package and check size
pkg <- devtools::build()
file.size(pkg) / 1024^2  # Size in MB
```

**If >5 MB:**
- Move large vignettes to pkgdown website
- Compress images in vignettes
- Remove unnecessary files
- Request size exception in cran-comments.md

### Issue: "Package has CRAN incoming feasibility NOTE"

**This is normal for new submissions!**

**Expected NOTE:**
```
* checking CRAN incoming feasibility ... NOTE
Maintainer: 'Michael Batech <michael.batech@gmail.com>'

New submission
```

**Action:** Document in cran-comments.md as expected

## Version Numbering for Future Releases

Follow semantic versioning:

**Current:** 5.0.0

**For updates:**
- **Patch** (5.0.1): Bug fixes only
- **Minor** (5.1.0): New features, backward compatible
- **Major** (6.0.0): Breaking changes

**When to update:**
- Critical bugs: Immediately (patch)
- New features: When ready (minor)
- Breaking changes: Carefully planned (major)

**Update frequency:**
- CRAN prefers fewer, well-tested releases
- Minimum 1-2 weeks between submissions
- Major updates every 6-12 months is reasonable
